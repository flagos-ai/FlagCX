# MUSA T4（Unified IR Inter）失败分析

分析对象：`C:\Users\Yan\Desktop\FlagCX_T4_logs_20261114_055038\t4-results-20261114_055038.HLibha\`
代码版本：`918e8f5`（日志 `environment.txt` 记录），平台 `USE_MUSA`、arch `mp_31`、
Default Device API 后端、2×4 逻辑拓扑、1K–16M factor 2。

## 1. 结论摘要

T4 不是"结果算错"，而是 **S20 的 Kernel 在设备侧发生了非法内存访问**：

- S16–S19 在正式运行（`t4-round1.log`）中 8 个 rank 全部 `PASS`。
- S20 `DevSignalStandalone(INTER+WORLD)` 的 Kernel 启动后，`streamSynchronize`
  在 8 个 rank 上同时返回原生错误 **700 = illegal memory access**，用例未打分即退出。
- 进程最终以 **SIGSEGV（rc=139）** 结束，这是 `main` 返回 1 之后退出阶段的次生崩溃，
  不是第一个故障点；它同时掩盖了程序本该返回的退出码 1。
- 本轮 `t4-round1` 跑在 CTA 强制同步**关闭**的配置下；该同步是 T2 K11 竞争的
  已验证修复（见第 5 节），验收脚本已改为默认打开。打开后 S16–S19 稳定通过，
  **S20 仍然 700**，说明 S20 与该竞争无关，是独立缺陷。
- 因为第一个 message size（1K）就中止，S21–S25 在 T4 拓扑下 **从未被执行过**，
  三轮稳定性更未开始。所以 "T4 只差一个 S20" 不能成立，S20 之后还有未知风险。
- 后续两次 A/B 已排除两条最直觉的猜测：`FLAGCX_SIGNAL_HOST_ENABLE=0`
  与 `FLAGCX_DEVICE_ONE_SIDED_FORCE_NET=1` 都不会让 S20 通过，
  并且失败地址在两种配置下完全相同（`0x1000cb40d88`）。详见 §4。

## 2. 证据链

### 2.1 失败点

`test/unittest/device_api/test_device_ir_unified_inter.cpp`：

```cpp
466:      launchKernelDevSignalStandaloneInterWorldS(devCommPtr, devResults, stream);
467:
468:      FLAGCXCHECK(devHandle->streamSynchronize(stream));   // ← 8 个 rank 都在这里失败
```

`t4-round1.log` 尾部：8 个 rank 依次打印
`test_device_ir_unified_inter.cpp:468 -> 1`（`1 = flagcxUnhandledCudaError`），
随后 `mpirun` 报告 `rank 5 ... exited on signal 11 (Segmentation fault)`。
S20 的 `S20 DevSignalStandalone(INTER+WORLD): PASS/FAIL` 一行从未打印。

### 2.2 原生错误码

同一目录下的 `native-*.log` / `trap-1k.log` 使用了 `runtime_errors.cpp`
（`musaStreamSynchronize` 的 LD_PRELOAD interposer），直接拿到了被 FlagCX 包装前的
原生错误：

```text
RUNTIME_DIAG pid=... musaStreamSynchronize stream=0x... native=700
  (an illegal memory access was encountered)
```

8 个 rank 全部为 700。`host_atomic_results.log` 里的独立原子探针则在 6 组
（device 分配 / host-mapped 分配 × store/load/fetchAdd）全部
`sync=0 no error`，说明"设备 64bit 系统域原子在 host 映射内存上不可用"这个
最简单的猜测不成立——探针是 1 block 1 thread、只访问本进程自己的映射。

### 2.3 SIGSEGV 是次生问题

- 失败地址 `0x1000cb40108` / `0x1000cb40d88` 落在设备地址区（同一日志里
  `buff=0x100db400000`、`devPeerPtrs=0x1000cc39000` 都是设备 VA），
  `Signal code: Invalid permissions (2)`。
- 6 份 `.rc` 全部是 `139`，而程序逻辑本应 `return 1`。
  原因：`FLAGCXCHECK` 在 `main` 中 `return RES;`，既不 `MPI_Finalize` 也不销毁
  DevComm，设备上下文已因 700 中毒，退出路径（驱动/运行时清理、proxy 线程）
  再踩到设备 VA 就变成 SIGSEGV。
- 影响：验收脚本 `musa_t4_acceptance.sh` 拿到的是 139 而不是 1，`results.txt`
  不会生成，三轮循环在第一轮就 `exit "$rc"`。读日志时不要先追这个 SIGSEGV。

## 3. S16–S19 为什么不能说明 S20 也没问题

`kernelDevSignalStandaloneInterWorldS` 与 `test/kernel/nvidia/device_ir.cu`
逐行一致（公共用例，MUSA 侧没有改写），所以问题在平台侧被它首次触达的路径上。
按用例序列梳理"谁第一个用到什么"：

| 用例 | 用到的能力 | T4 结果 |
| --- | --- | --- |
| S16 DevBarrier | Inter/World barrier：FIFO 远端 signal + **只读** `signalBuffer`（网络面） | PASS |
| S17 DevTeamResolution | 单向 Put，不使用 signal 槽位 | PASS |
| S18 DevPut+PutValue | FIFO Put / PutValue | PASS |
| S19 DevGet | FIFO Get | PASS |
| **S20 DevSignalStandalone** | **`ResetSignal`（写 signal 两面 + shadow）、`ReadSignal`、`SignalInc/Add`、`WaitSignal`（用户槽位 0–11）** | **700** |

即：**S20 是整个 T4 中第一个读写"用户 signal 槽位"的用例**。barrier 只用到
`barrierSignalBase=18` 之后的槽位，而且只有两种动作：FIFO 远端 signal（写对端网络面）
与对网络面的**原子读**——它从不 `reset`，也从不读本地面。

配置对照进一步缩小了范围（两次都是 CTA 同步关闭、同一份 `918e8f5`）：

| 运行 | `SIGNAL_HOST_ENABLE` | 单向路径 | 结果 |
| --- | --- | --- | --- |
| T3 `test_device_ir_unified_intra` | **0**（GDR 设备内存 signal 面） | — | 通过，含 INTRA/WORLD 版 S20 |
| T4 `t4-round1` | **1**（/dev/shm host 映射 signal 面） | p2pSignal=1 | S20 700 |
| T4 `native-force-net-1k` | 1 | **p2pSignal=0、forceNet=1**（走纯 Net，不做本地 P2P 原子） | S20 仍然 700 |

`native-force-net-1k` 这一组很关键：它把"直接对本地 peer 的 host 映射面做
64bit 系统域 `fetchAdd`"这条路径关掉了（`one-sided paths p2pSignal=0 net=1 ... forceNet=1`），
S20 依旧 700。所以**主因不是跨进程对称面的原子 RMW**。

从日志确认 signal 面布局正常、指针本身不越界（`t4-round1.log`）：

```text
one-sided buffers allocated (signals=90, counters=18, contexts=4)
signalBuffer sigSize=2880 (count=90 ctx=4)          # 90 = 18 用户槽 + 2 nodes × 36 barrier 槽
setupHostSignals(SHM): rank 0 local=0x81e43fe000 network=0x81e43ff000 mrHost=0x7f192c5d3000 peers=4
buildIpcPeerPointers ... devPeerPtrs=0x1000cc3xxxx
```

`local` 与 `network` 相差 0x1000（planeStride = 4096 ≥ 2880），`mrHost` 是 host VA
（NIC 注册用），互不混淆；`_contextId × signalCount + slot` 最大索引 3×90+11=281 < 360 字，
在两面范围内。

## 4. 根因定位：假设与排除记录

### 4.1 已排除

| 假设 | 判别实验 | 结果 |
| --- | --- | --- |
| host 映射 signal 面（`FLAGCX_SIGNAL_HOST_ENABLE=1`）导致 | `FLAGCX_SIGNAL_HOST_ENABLE=0` 重跑（`t4-results-20261114_065248.A1L9df`） | **排除**：S16–S19 仍全 PASS，S20 仍在 `cpp:468` 失败，SIGSEGV 地址与 `native-force-net-1k` 完全相同（`0x1000cb40d88`） |
| 本地 peer host 映射面的 64bit 原子 RMW | `FLAGCX_DEVICE_ONE_SIDED_FORCE_NET=1`（`native-force-net-1k`，`p2pSignal=0 forceNet=1`） | **排除**：S20 仍失败 |
| signal 面指针越界 / 两面混淆 | 指针与索引核算（见上） | **排除**：索引最大 281 < 360 字，两面各在独立 4KB 页 |
| 端到端逻辑写错（Reset/Read/Wait/Signal 语义） | T3 单节点同代码同配置 S20 通过 | 语义本身可用 |

### 4.2 当前收敛到的位置

两次失败/通过的分界线不是"signal 面在哪块内存"，而是 **comm 是否跨节点**：

| 配置 | 节点 | S20 | 说明 |
| --- | --- | --- | --- |
| `=1` | 2×4 | 失败 | 网络面对 + 本地面 |
| `=0` | 2×4 | 失败 | 仅网络面（gdr 设备内存），`localSignalBuffer=NULL` |
| `=0` | 1×8（T3） | 通过 | 同一份 Reset/Read/Wait/Signal 代码 |

因此在 2 节点 + `=0` 这一组的运行里，S20 相对 S16 真正多出来的动作只有三项，
且都在**用户 signal 槽位 [0,18)** 上：

1. `ResetSignal` —— 全套用例里**唯一**往 signal 面写 `Atomic::store` 的动作
   （S16 的 barrier 只对 signal 面做 load；它只对 shadow 面做 `+=1`）；
2. `ReadSignal` —— 用户槽位上的原子读；
3. `WaitSignal` —— 用户槽位上的自旋等待（coop 覆盖 THREAD / WARP / BLOCK 三种）。

**H2：`ResetSignal` 的 64bit 系统域 release store 在该平台/该上下文下不可用。**
优先级最高：它是 S20 唯一全新的写动作，且在 1 节点上下文里可正常工作，
在 2 节点上下文里失败——差异可能来自跨节点上下文对 signal 面访问属性
（atomic 代理/缓存属性）的配置不同。

**H3：S20 的失败其实来自 S19 遗留的异步错误，而不是 S20 自己。**
本地有先例：2026-11-12 那轮出现过"S16 启动前已存在 error 98"。
`cpp:468` 的 700 是 `musaStreamSynchronize` 报的**粘性**错误，
若某个更早的异步操作（S19 的 RDMA Get 完成路径、S19 kernel 退出后的
proxy 侧写）在 S19 的 sync 之后才落到设备上，就会被记到 S20 的同步上。
判别方法只能是"跳过 S16–S19、只跑 S20 原语"的独立诊断（见 §6 第 2 步）。

**H4：用户槽位的中继编码与 barrier 槽位不一致（proxy 侧）。**
两者调用同一个 `enqueueSignal(...)`，静态上一致，可能性最低；
当前 INFO 级日志里 signal 触发器没有任何记录，无法自证是否投递。

### 4.3 平台侧必需运行时变量（2026-11-14 官方基线实测）

用文档 §13.3.5/§13.3.6 的纯公共基线（只有 `FLAGCX_USE_HETERO_COMM=1`、
`FLAGCX_VMM_ENABLE=0`、`LD_LIBRARY_PATH`）在本平台实测：

- T3（单节点、8 ranks）：`rc=0`，S16–S25 各 120 条 PASS，`=== Final Result: ALL PASS ===` 一次。
  说明单节点不需要任何厂商变量，且 T2 交接增量之后 **T3 没有回归**。
- T4（2 逻辑节点）：**在 `flagcxDevCommCreate` 就失败**（`test_device_ir_unified_inter.cpp:103 -> 9`）：
  `ibv_reg_mr failed with error Invalid argument` → `ibrc_adaptor.cc:2110 -> 2`
  → `netSignalReady=0` → `neither signal IPC nor Net fallback is available`
  → 后端返回 `flagcxNotSupported(9)`，随后退出阶段 SIGSEGV（rc=139）。

结论：**`FLAGCX_DMABUF_ENABLE=1` 在本平台是 2 节点通信的必需项**——不开 DMA-BUF，
设备内存无法注册成 IB MR。这条要按 §13.3.9 写进交付报告（作为"厂商补充的
运行时变量"），不能算作改动测试或缩小范围。`FLAGCX_MEM_ENABLE` 不是必需项
（纯基线下同样走到了 DevComm 创建）。

### 4.4 假设演化（含已否定的版本）

| 版本 | 内容 | 判别实验 | 结论 |
| --- | --- | --- | --- |
| V1 | host 映射 signal 面本身不可用 | 2 节点 `SIGNAL_HOST_ENABLE=0` | 否定：仍 700 |
| V2 | 本地 peer host 面的原子 RMW | 2 节点 `FORCE_NET=1`（`p2pSignal=0`） | 否定：仍 700 |
| V3 | 落在"设备映射 host 窗口"里的 64bit 系统域 store 不可用 | 1 节点 `SIGNAL_HOST_ENABLE=1`（`t3-hostonly`，rc=0、S20 与全量 S16–S25 通过，`setupHostSignals` 出现 peers=8） | **否定**：host 窗口上的 reset/store/read/wait/direct-P2P 原子全部正常 |
| V4（当前） | 只有当 signal 面被 **注册成 IB MR 并启用跨节点中继** 后，对该面的 64bit 系统域 store 才失效 | 待定 | — |

V4 的依据是把全部实测按"signal 面是否被 NIC 注册"重排：

| 配置 | 节点 | signal 面 | NIC MR | S20 |
| --- | --- | --- | --- | --- |
| T3 默认 | 1 | 普通设备堆 | 否（nInterPeers=0） | 通过 |
| T3 + `SIGNAL_HOST=1` | 1 | /dev/shm 窗口 | 否（nInterPeers=0） | **通过（本轮新增）** |
| T4 `SIGNAL_HOST=1` | 2 | /dev/shm 窗口 | 是 | 700 |
| T4 `SIGNAL_HOST=0` | 2 | DMABUF 设备内存 | 是 | 700 |

同时 S16 在**同一条已注册 MR 的面上**只做原子 load 就通过，S20 是套件里唯一对该面做
64bit 系统域 `Atomic::store`（`ResetSignal`）的动作。纯环境变量的组合到这一步已经
无法再分离变量，下一步必须上设备侧诊断（只读/只写/只等分别跑）。

### 4.5 S20 根因收敛（2026-11-14 深夜，真机对照）

在真实 T4 程序（`test_device_ir_unified_inter`，2×4，1K）上逐个注释 `Barrier<World>::sync()`
的相位，得到确定的对照：

| 变体 | 改动 | S20 |
| --- | --- | --- |
| B | 跳过 `_inter.sync()`，保留 `_intra.arrive/wait` | **PASS（700 消失）** |
| A2 | 跳过 `_intra.arrive/wait`，保留 `_inter.sync()` | **仍 700**（rc=139） |
| 拆分 | 把 `_inter.sync()` 换成 `_inter.arrive()`+`_inter.wait()`（同一对象内） | 仍 700 |

⇒ **故障只需要 World 同步里的 inter 相位；intra 相位无关。** 而同一套
`Barrier<Inter>::sync()` 在 INTER-team 单独使用时（探针 mode 10、S16 的 INTER 同步）
是正常的；S16 的 World `arrive`+`wait`（两个独立 IR 入口、两个独立对象）也正常。

⇒ 当前最窄的判断：mcc 5.1.0 对“在单个对象内把 `_inter.arriveImpl` 与 `waitImpl`
融合进同一段 inline 代码”这条 World 同步路径生成了错误的设备代码（该工具链已有
`failed to process CFG` 等代码生成问题记录）。这不是 FlagCX 的逻辑错误。

尝试记录：

- 在 `Barrier<World>::sync()` 内部拆成 arrive+wait（同一对象）——**无效**；
- 在 IR 层用两个对象（`bar`/`bar2`）在**同一个** IR 函数内 arrive+wait——**更糟**，
  S16 也一起崩（rc=139，无任何用例输出）。说明关键不在于“几个对象”，而在于
  **内核里两次独立的 IR 入口调用**。

待验证的修复：让统一 IR 的 `flagcxDevBarrierSync(WORLD)` 改调
`flagcxWorldBarrierArriveS` + `flagcxWorldBarrierWaitS` 两次独立调用（与 S16 内核同形）。

## 8. 当前状态与未决问题（2026-11-14 收口）

### 8.1 问题一：S20 设备非法访问（已定位根因）

现象：

- `test_device_ir_unified_inter` 在 2 逻辑节点、第一个 size（1K）就失败；
  `test_device_ir_unified_inter.cpp:468`（S20 的 `streamSynchronize`）8 个 rank 同时
  打印 `-> 1`（`flagcxUnhandledCudaError`），S20 的结果行永不出现。
- LD_PRELOAD 拦截 `musaStreamSynchronize` 拿到原生码 **700（illegal memory access）**。
- 进程随后在退出阶段 SIGSEGV，`rc=139`（掩盖了本该返回的 1）。
- 与 `FLAGCX_SIGNAL_HOST_ENABLE`(0/1)、`FLAGCX_DEVICE_ONE_SIDED_FORCE_NET`(0/1)、
  `FLAGCX_MUSA_FORCE_CTA_SYNC`(0/1) 都无关，任一组合都复现。

根因（已用真机 A/B 确认）：

mcc 5.1.0 / mp_31 对**含动态 `__trap()` 的设备 kernel** 生成异常资源属性
（`numRegs=256`、`localBytes=16384`、`maxThreadsPerBlock=0`，见
[musa_trap_resource_issue](./musa_trap_resource_issue.md)），kernel 首次访问局部内存即
非法地址。S20 的 kernel 是套件里最大的一个（12 个 combo 全展开），因此最先越界；
这也解释了为什么任何“重构 World 同步”的改动都会连带把 S16 一起弄崩。

证据：

| 改动 | S20 | 进程 |
| --- | --- | --- |
| 基线 | 700 | rc=139 崩溃 |
| 跳过 `Barrier<World>::sync()` 的 `_inter` 相位 | **PASS** | rc=1 |
| 跳过 `_intra` 相位 | 700 | rc=139 |
| `_inter` 拆成 arrive+wait（同一对象） | 700 | rc=139 |
| IR 层两对象 / 两次独立 IR 调用 | 更糟：S16 也崩 | rc=139 |
| `default_comm_traits.h` 中 trap 全部编译掉 | **PASS** | rc=1 |

修复方向：`FLAGCX_DEVICE_TRAP()` 本身（device pass `__trap()` / host pass
`__builtin_trap()`）**保持不变**；在 `default_comm_traits.h` 内为 MUSA 增加门控别名，
使该文件的“配置合法性检查”（fence 合法性、GDA 能力、FIFO 终端状态）在 MUSA 设备
编译时不再生成 trap 指令。这些检查的上位门禁在 Host 侧（能力探测 /
`flagcxNotSupported`），不会削弱保护。`platform_traits.h` 的同类 trap 点未改动，
若其它 kernel 触发同一资源异常需另行处理。

### 8.2 问题二：跨节点数据面校验失败（未定位）

现象：

- S17 DevTeamResolution、S18 DevPut+PutValue、S19 DevGet、S21–S24 全部 FAIL，
  **但不崩溃**；失败来自逐字节 / `hostRes` 校验不通过，说明数据没到或不可见。
- **非确定性**：S17–S19 在 7 次同配置运行中只有 2 次全 PASS（`t4-round1`、
  `cta-sync-original-range`），其余 5 次全 FAIL；与 CTA 同步开关没有稳定相关性。
- S21–S24 此前从未被执行过（进程总在 S20 崩溃），当前是首次观测。

在 S20 崩溃被消除之前，这个问题被 700 掩盖；消除后它成为 T4 的主要阻塞。

### 8.3 附带确认

- **无回归**：T3 用纯公共基线（仅 `FLAGCX_USE_HETERO_COMM=1`、`FLAGCX_VMM_ENABLE=0`）
  单节点 8 rank `rc=0`，S16–S25 各 120 条 PASS；T2 用 `-R 2` `rc=0`，8 rank 全部
  `=== Overall: PASS ===`，K11/K12/K13 PASS。
- **平台必需项**：`FLAGCX_DMABUF_ENABLE=1`。纯基线下 2 节点会在
  `flagcxDevCommCreate` 返回 `NotSupported(9)`（`ibv_reg_mr` EINVAL →
  `netSignalReady=0`）；T2 还必须带 `-R 2`（不带则 rc=1）。
- **已排除**（均为真机对照）：host 映射 signal 面、IB MR、直接 P2P 原子 RMW、
  Net 强制回退、rank 内 CTA rendezvous、单对象 arrive+wait 拆分、proxy 终端错误
  （加了日志后一条都没有）、以及早期探针（探针缺少 window/devMem 初始化，
  与真实用例不符，其结论作废）。

## 5. 更正：CTA 强制同步是已验证的竞争修复，不是要摘掉的实验项

前一版分析把 `FLAGCX_MUSA_FORCE_CTA_SYNC=1` 当成"实验配置、不能作为验收依据"，
这个判断是错的，需要撤回：

- T2 的 K11 用例存在真实的竞争——CTA A 的写与 CTA B 的 `reset` 之间没有跨 CTA
  的先后保证，会偶发 hang；此前已用实测确认，只有加上 rank 内 CTA 到达同步才稳定。
- 需求文档 6.4 本身就要求 "reset、send、wait 之间要有跨 rank 所需的同步，
  避免 lost-signal race"，以及 "cooperative API 必须由整个 coop group 一致调用"。
  加入 rank 内 CTA 同步是该条款的**实现**，不是绕过用例。
- 日志也印证这一点：`native-1k` / `native-force-net-1k` / `trap-1k`（CTA 同步关闭，
  `epochBuffer size=576`）S17–S19 全部 FAIL；`native-cta-sync-1k` /
  `cta-sync-original-range`（打开，`epochBuffer size=584` 且打印
  "EXPERIMENTAL rank CTA rendezvous enabled"）S16–S19 稳定 PASS。
  `t4-round1` 那次关闭状态下 S17–S19 侥幸 PASS，正是偶发性。

因此 T4 验收应当**与 T2 交接配置对齐、固定打开**该同步
（`test/unittest/device_api/musa_t4_acceptance.sh` 原来写成 `=0`，是本轮抖动的原因，
已改为默认 `1`，需要 A/B 时由调用者在外部覆盖）。

重要的是：**S20 的 700 与该开关无关**——`cta-sync` 两组在打开状态下 S16–S19 全过，
S20 依旧 700。所以 S20 是一个独立的、与该竞争无关的缺陷。
