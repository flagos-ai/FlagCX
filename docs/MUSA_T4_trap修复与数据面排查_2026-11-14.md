# T4 trap 修复与数据面排查

本轮只修改本地实现、独立诊断探针和运行脚本。没有修改公共 T1–T4
测试的 kernel、Host 测试代码、参与范围和判定条件，没有改镜像构建方式。
主库继续由 mcc 管理各编译单元的镜像及注册。

## trap 的处理

不修改全局 `FLAGCX_DEVICE_TRAP()` 分派，也不增加 `__builtin_unreachable()`。
针对受影响的 MUSA Default 路径：

- MUSA 当前只提供 Proxy Net，分派直接实例化 Proxy，避免把不可用 GDA
  的 trap 分支编进每个 kernel。直接实例化未实现 GDA 会在编译期报错。
- Barrier 配置、fence 和 FIFO terminal 检查仍然执行；失败时通过系统域
  CAS 发布首次错误，不生成动态 trap。正常路径的通信和 barrier 相位保持原样。
- 每个 DevComm 有独立的 Host 映射错误字，纯 INTRA 且没有 FIFO 也能上报。
  有 FIFO 时同时发布到其 terminal word，Proxy 将设备错误接入现有失败处理。
  等待循环检查本地错误以便退出；这不是跨 rank 的错误广播协议。
- Host device/stream/event 同步及完成查询检查当前 GPU 的已注册错误字。
  错误保持到 owner 销毁，不把失败误报为成功。检查粒度为当前 GPU，可能
  返回该 GPU 上另一个 Comm 的错误；不声称能够精确归属到某一条 stream。
- 注册表在 owner 释放前注销；创建失败也清理。所有库和测试对象必须一起
  重编，因为内部 Comm 布局新增了指针。

独立回归探针 `test/unittest/musa_platform/musa_device_error.cu` 覆盖：
动态正常/错误条件、没有 FIFO 的 INTRA 场景、两个 FIFO 的错误发布、首次
错误保留、原生同步成功而 FlagCX 同步返回设备检查错误、注销后不再访问旧地址。
它不替代 S20 或完整 T4 验证。

容器内先编译主库和探针：

```bash
cd /workspace/FlagCX
export LD_LIBRARY_PATH="$PWD/build/lib:/usr/local/musa/lib:/usr/local/musa/lib64:${LD_LIBRARY_PATH:-}"
timeout --kill-after=5s 600s make -B -j1 \
  USE_MUSA=1 COMPILE_KERNEL=1 DEVICE_HOME=/usr/local/musa MUSA_ARCH=mp_31 &&
timeout --kill-after=5s 300s make -B -C test/unittest/musa_platform device-error \
  DEVICE_HOME=/usr/local/musa MUSA_ARCH=mp_31 &&
timeout --kill-after=5s 60s test/unittest/musa_platform/build/musa_device_error 0
```

正常控制分支必须成功；故意触发错误的分支必须得到 `flagcxInvalidUsage`，
且原生执行不能出现 700。仍需检查正式 S20 的资源属性并完成实际运行，不能
用移除 trap 或探针通过宣称 T4 已通过。

## 数据校验：先区分 Host 读取与网络问题

公共 `test_device_ir_unified_inter.cpp` 的 S17、S18、S19、S21–S24 等位置
在 `deviceMemcpy(...DeviceToHost, stream)` 后立即读取 `hostRes` 和接收数组。
MUSA adaptor 对非空 stream 调用 `musaMemcpyAsync`。此前的
`streamSynchronize` 在这些 D2H 之前，因此没有显式等待这些拷贝完成。
是否恰好同步取决于运行时及 Host 缓冲区类型；目前只是待验证因素。

实现侧增加可选 `FLAGCX_MUSA_SYNC_D2H=1`：只在异步 D2H 后同步同一条
stream，默认行为不变。验收脚本会记录并传入 MPI。该开关是诊断变量，不能
把它开启后的结果当作默认异步语义已经正确的证据，也不能直接断言网络已修复。

完成 trap 修复后的全量重编，顺序运行相同配置的两个对照：

```bash
cd /workspace/FlagCX
# 基线，先重编全部库、IR 和 Host 测试程序。
FLAGCX_MUSA_SYNC_D2H=0 ROUNDS=1 BUILD=1 \
  bash test/unittest/device_api/musa_t4_acceptance.sh
# 诊断对照，使用同一批二进制和同样 1K..16M 范围。
FLAGCX_MUSA_SYNC_D2H=1 ROUNDS=1 BUILD=0 \
  bash test/unittest/device_api/musa_t4_acceptance.sh
```

两次调用各自打印 `OUTPUT=`，保存环境、构建日志、实际命令、退出码和完整
round 日志。应重复对照确认稳定性；一次诊断 PASS 也可能来自时序扰动。

若只有同步 D2H 对照稳定通过，进一步用独立探针验证拷贝完成语义，汇报公共
Host 驱动的同步缺口，保持原测试不变。若仍失败，继续按以下边界定位：

1. 对照每个用例的 kernel 内校验与 Host 回读，确认失败产生的位置；Host
   回读同步只能排除回读未完成，不能证明远端数据在 kernel 内已经可见。
2. 保持原始最大分配规模，记录 MR index/base、src/dst offset、实际 peer
   与 context；核对偏移始终相对注册基址，signal 的 context stride 只加一次。
3. 对照 FIFO produced/completed、原生 CQ 完成与 GET visibility flush，确认
   completion 发布发生在可见性保证之后。PUT 端 CQ 完成不能单独证明远端 GPU
   已可见；必须检查接收方的 acquire/flush 路径及其覆盖的 MR 范围。
4. 最后单独 A/B 强制 Net 路径和 CTA 开关；每轮只改一个变量。验收默认仍为
   `FLAGCX_MUSA_FORCE_CTA_SYNC=1`，不以修改测试参与范围换取 PASS。

本地只有源码和脚本检查条件，没有 MUSA SDK/GPU；以上 GPU 探针、S20 资源
检查和两组 T4 对照尚未运行。T4 状态仍为待验证。
